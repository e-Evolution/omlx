Local AI Agents Finished a Real Project on One Mac: What It Took

What broke in oMLX and gentle-shell, how we fixed it, and the fixes we're contributing back to both projects.

Can local models, one Mac and only open-source tools finish real work from beginning to end, without someone watching every step?

I am the lead maintainer of ADempiere, an open-source ERP, CRM and SCM project. We had a concrete, useful task to test that question on: turn our PDF manuals and older screenshots into wiki documentation, with images of the new ADempiere version and an assistant that answers questions.

With the server and harness fixes described below applied during the pilot, the project met its objective. The documentation was completed end to end on a single Apple workstation configured for local AI. This article is the short version. The full field report has the method, every number and its limits.

The tools, for anyone new to them

  • oMLX, by jundot, runs open AI models locally on Apple Silicon Macs. It keeps a prompt cache on SSD, so an agent that re-sends a long conversation does not pay for all of it again.
  • gentle-shell, by Alan-TheGentleman, is a harness for the pi coding agent. It adds the agent workflow: orchestration, a todo tool, review integration and subagents that run as separate processes.
  • Qwen models, specifically Qwen3.8-27B in a 4-bit build with Multi-Token Prediction and TurboQuant 4-bit KV cache, running on an Apple M5 Max with 128 GB of memory.

Several agent sessions shared one model. They read whole source files and took screenshots, so prompts were large: across 1,260 recorded requests, the median was 107k tokens and the 90th percentile 168k. At that size, the prompt cache decides whether a turn costs one second or several minutes.

What broke when we left it alone

The goal was simple to state: leave the machine working until every job finishes. On the stock release (oMLX v0.7.0) it did not:

  • Lost work under memory pressure. Several long prompts at once reached the memory guard's hard limit. Requests were aborted mid-prefill, all progress was lost, and the agents stopped and waited for a human.
  • Concurrency made it worse. In a three-request benchmark, running them together took 538 s against 246 s one by one, with 6 aborts.
  • Batched decode was slow and, on that runtime, could go wrong. Short rows in a padded batch attended over padding.
  • The prompt cache collapsed in bursts. Average reuse was high, but single turns lost 70k–170k cached tokens.

None of these showed up in a unit test. They appeared only when real agents ran for hours against a real server.

How we worked

Before writing code, we wrote six falsifiable premises, each tied to a benchmark on the same machine, model and prompts, against the upstream release. Nothing counted as done until its premise passed.

The changes were made test-first, one reviewable commit per behaviour, with an independent review on each slice. When something failed, we traced it in server logs and in a small client-side recorder that captured the exact payload of every request, then fixed it with a regression test first.

That last tool mattered more than expected. Comparing consecutive requests byte by byte, and matching the first changed byte with the position where the server's cache diverged, is what found the largest problem of all, and it was not in the server.

What we propose for oMLX

1. Batched TurboQuant decode (PR #4441). When rows of different lengths decode together, the shorter rows are left-padded. The batched path let the padding into attention and dequantized the whole context on every step. The fix makes each row attend only to its own slice. On recent upstream code, with a batch of three restored prompts (20k, 45k and 135k tokens), batched decode became 5–12× faster per row, the batch phase went from 345 s to 66 s with MTP on, and peak memory dropped by 11–15 GB. Two commits, 28 tests.

2. Prefill after an SSD cache hit (PR #4442). When a long prompt reuses a cached TurboQuant prefix from SSD, the rest of the prompt was prefilled against the compressed prefix, 2.4× slower than processing the same positions cold. A one-off dense copy of the restored layers (0.43 s) brings it to 0.92× of cold. Two commits, 16 tests.

3. Pause and resume instead of abort (proposal in discussion #4440). Under memory pressure, the server pauses one request, saves its state to the SSD cache, and resumes it later on the same stream, instead of aborting everything in flight. A request that can never fit gets a clear error with the numbers in 0.1 s, so the agent can compact its context and retry. In a forced-pressure test, 9 of 9 requests finished, against 3 of 9 on recent upstream code. With MTP off, 12 forced pauses produced identical output. It is about 13,000 changed lines, two thirds of them tests, so it is proposed as a stack of 12 small pull requests, every new behaviour behind an opt-in switch, waiting for the maintainer's view before any is opened.

On the fork used day to day, 333 live agent requests at up to 5 at a time ran with 0 memory aborts, and 94.8% of prompt tokens came from the cache in that log window. In the benchmarks against the upstream code of the time, two concurrent 130k-token prompts peaked at 44 GB instead of 116 GB and finished about 3× faster, and unattended agent batches finished 3 of 3 times against 0 of 3 on v0.7.0.

What we propose for gentle-shell

The largest single cache loss in the whole investigation was in the harness. While todos were open, gentle-shell's todo extension rewrote the system prompt on every user prompt, including a "stale" counter that changed each time. On the tested setup, every rewrite broke cache reuse from that point onward.

Nothing failed and every harness test passed. Agent turns just took minutes instead of seconds.

Over about a day and a half of real use, that meant roughly 1.05 million tokens processed again, about 80–85 minutes of GPU time. The fix moves todo state out of the system prompt into conversation messages, sent only when the list changes. Requests that rewrote the system prompt went from 21 of 61 to 0 of 90, and re-prefills above 20k tokens went from one or two per hour to zero. The fix is ready, its 63 todo tests pass, and it is tracked in issue #1367.

The lesson applies to any agent harness: prompt-stability tests catch the rewrite itself, but only a server with an observable cache shows what it costs.

What this does and does not show

The numbers come from my own runs on one Apple M5 Max and one model family, mostly one run per configuration. They are evidence, not an independent reproduction. The fixes are proposals; none is adopted upstream yet, and they are not guarantees for smaller machines. The full report lists every limit next to the number it qualifies.

Why we are sharing it

oMLX and gentle-shell are open source, built by people who share their work with everyone. We like that philosophy, and contributing back is how we take part in it. My thanks to jundot and Alan-TheGentleman for the projects that made this pilot possible.
