Introduction

This article addresses a concrete question: is it possible to complete real work from beginning to end using local models, consumer hardware, and only open-source technology?

To investigate it, we developed a documentation pilot: turning PDF manuals and older screenshots into wiki documentation, with images of the new ADempiere version and an assistant that answers questions. The implementation combined the oMLX inference server, the Gentle Shell agent harness, and open-weight models from the Qwen family, running on a personal workstation.

I am the lead maintainer of ADempiere, an open-source project for ERP, CRM, and SCM. Its official repository provides public access to the source code and development history, giving readers context for the project behind this pilot. I also lead a company specializing in the development, support, and professional maintenance of solutions based on this technology. That experience helped us choose a concrete, useful task with verifiable results.

The purpose was not to compare this configuration with frontier models or tools such as Claude Code or Codex, but to establish whether it could complete the proposed work, identify the obstacles, and document the conditions needed to make it possible.

Below, I share the experience, the problems encountered, the solutions developed, and the results obtained, together with the limitations of the evidence.

Executive summary

We tested whether local models on consumer hardware, using open-source tools, could carry out useful documentation work without constant human intervention. The pilot used Qwen models served by oMLX on an Apple M5 Max with 128 GB of memory, with pi and gentle-shell coordinating agents working on an ADempiere wiki.

  • For oMLX: TurboQuant batched-decode and restored-prefix prefill fixes improved measured performance. A proposed pause-and-resume stack kept requests alive under forced memory pressure.
  • For gentle-shell: A todo-driven system-prompt rewrite caused substantial cache loss. The tested fix moves todo state into conversation messages to keep the system prompt stable.

With the proposed server and harness fixes applied during the pilot, the project met its objective: the documentation was completed from beginning to end in wiki format, with images of the new ADempiere version and an assistant that answers questions, using local models, consumer hardware and open-source tooling. The benchmarks document improvements in performance, memory use and stability that supported that outcome; they do not independently audit the wiki's content. Historical batch results, newer upstream comparisons and an unpaired live run answer different questions.

Results are limited to one Apple consumer workstation configured for local AI and one model family. Upstream merged PR2 as #4442 and PR1's fix as #4453 on 2026-10-12; the other fixes are proposals, not claims of upstream adoption, and none is a guarantee for smaller machines.

About this report

A field report for the maintainers of two projects: oMLX, the inference server, and gentle-shell, the agent harness. It follows one developer workstation running coding agents unattended: how the work started, how each problem was measured, what was changed in a fork, how it was validated, and which parts we would like to contribute upstream. Both projects were improved with the same method: measure on real traffic, attribute each loss to a cause, fix test-first, and validate against the other side.

Scope. The oMLX work started on v0.7.0 and is now based on v0.7.1.dev1, upstream main 013bc3f3. This is a field report on specific versions, not a general validation of the current fork or of today's upstream main. The C7 runs and the live production run used upstream oMLX main at b7c7929e, the fork branch at the commits named in each section, and gentle-shell main at aa2c0389. Two re-validations are newer: the TurboQuant fix (PR1) on upstream main 25aebb3e, and the whole fork against main c0b1056b, which also surfaced a second upstream TurboQuant defect (PR2). The branches proposed upstream are rebased on main 013bc3f3.

Upstream bug found along the way (oMLX). In batched decode with TurboQuant, left-padded short rows attend over zero padding columns, and every padded decode step goes through a slow dequantize-everything path. In synthetic tests the short row's output norm drops to 0.32× of the reference. With Lightning MTP, padded verify forwards also miss the per-row path, and the verify-tail rollback re-quantized the whole batch every cycle; upstream has since fixed the rollback in #3127. The use case

The setup is one Apple M5 Max (128 GB) serving one local model to several pi coding-agent sessions. pi runs the gentle-shell harness (package gentle-pi) on top, which adds the agent workflow: orchestration, a todo tool, review integration and subagent delegation. Subagents run as separate pi processes, each with the same harness. The sessions read whole source files and take screenshots. Prompts are large: across 1,260 recorded requests the median was 107k tokens and the p90 168k. Each turn re-sends the growing conversation, so the prefix cache decides whether a turn costs 1 second or several minutes.

The goal was simple to state: leave the machine working until every job finishes. That means using free memory for concurrency, never throwing away completed work, and pausing rather than aborting when memory is tight.

What broke on stock v0.7.0

  • Several concurrent long prompts reached the memory guard's hard watermark. Requests were aborted mid-prefill, all prefill progress was lost, and the agent stopped waiting for a human.
  • Raising concurrency made things worse. In a 3-request mixed benchmark, concurrent finished in 538 s against 246 s serial, with 6 aborts.
  • When batched decode did run, short rows in a left-padded TurboQuant batch produced degenerate output.
  • Prefix-cache reuse was high on average but collapsed in bursts: single-turn losses of 70k–170k tokens.

How it developed

The question

After the 0.7.0 memory-guard tiers landed, the question was whether a request could pause when memory runs out and resume when it frees, instead of aborting. We checked where that belongs, client or server, and settled on both. The pi extension pauses and auto-continues. The server keeps prefill progress and parks instead of aborting.

Premises before code

We wrote six falsifiable premises (P1–P6), each tied to a benchmark that runs against upstream v0.7.0 on the same machine, model and prompts. Nothing counted as done until its premise passed against upstream.

Implementation in small reviewed slices

The work was done test-first, with one reviewable commit per behaviour and an independent review on each slice (four review lenses on the high-risk ones). It went into a fork branch off v0.7.0 and was packaged as a side-by-side app for daily use.

The batching surprise

Real concurrent use exposed the padded-attention corruption and very slow batched TurboQuant decode, about 1.5 tok/s per row. Fixing the correctness bug and adding a single-launch ragged kernel brought per-row decode to about 13 tok/s.

The cache-reuse investigation

Once nothing aborted, the remaining cost was re-prefill. We recorded every request payload with a small client-side recorder and attributed each cache break to a cause. About 2.7M tokens were re-prefilled over roughly 1.5 days. The largest cause was in the gentle-shell harness and two were in the server; all three were fixed.

Harness and server, tested together

Testing the gentle-shell harness against the running oMLX server, with server-side monitoring, exposed a cache invalidation that neither side showed on its own: while todos were open, the harness rewrote its system prompt on every user prompt. The fix went to gentle-shell, and the method became part of this report (details).

Live validation

Recorded traffic and daily use helped validate the changes exercised by those workloads. Structured logs (cache outcome, TTFT breakdown, eviction summary) supported the measurements; features tested only in unit or forcing tests are identified separately.

Pause and resume, end to end

A forcing benchmark showed that the prefill park works but cannot save a batch, because decoding rows and image prompts still aborted. We built the full cycle: decode pause, memory-aware resume, a never-fits error and parkable image prompts. Its first validation run failed in several ways. Each failure was traced in the logs and fixed test-first, until every request finished under forced pressure with 0 aborts.

Live production run

The packaged fork (0.7.0-fork.5) then served real unattended agent work for 1 h 39 min, with the concurrency limit raised live from 3 to 5. It logged 0 memory aborts and served 94.8% of prompt tokens from the prefix cache. Memory stayed far from the pressure line, so pause and resume never fired.

Upstream defect: slow suffix prefill after a restored TurboQuant prefix

Field illustration of concurrent prefill from the earlier fork.5 recordings, not a recording of the restored-prefix fix or its paired benchmark below.

Tracing P1's missing TTFT gain on c0b1056b led to a second upstream TurboQuant defect. After a paged-SSD prefix hit, the uncached suffix of a prompt prefilled about 2.4× slower per token than a cold prefill of the same positions. It reproduces on main, so it is not a fork bug, and with TurboQuant off the two take the same time.

Mechanism

  • A paged-SSD hit restores TurboQuant layers as quantized TurboQuantKVCache objects (#1842), and the scheduler keeps them quantized while it prefills the suffix.
  • Every chunk of every TurboQuant layer then attends to the whole quantized prefix through the tiled quantized-attention path, never dense SDPA, so the cost grows with the prefix length.
  • The prefill capacity reservation reports across 1 caches after such a restore instead of 16, because only the unquantized last layer is a plain KVCache it can plan. That line is a symptom, not the cause.

Fix

Before a suffix that needs more than one prefill chunk, the scheduler copies the restored TurboQuant layers into dense KVCache layers once, so suffix chunks run the same dense path as a cold prefill. At the end of prefill only the suffix is quantized and appended to the original TurboQuant cache, so the restored prefix codes are reused bit for bit instead of being quantized again. The step runs only when the dense layers, sized for the whole prompt, fit under the prefill peak target, the same gate as the prefill reservation; otherwise it logs that it kept the quantized prefix. A one-chunk suffix, such as a chat turn, keeps the current path. Two commits with 16 tests, on main 013bc3f3.

The strategy: pause, don't abort

The most valuable idea of the project was a change of question. When memory reaches the hard limit, the stock server aborts in-flight requests, which throws away every token they prefilled and generated. We asked whether the server could pause a request instead. The paged SSD cache already existed and makes a pause cheap.

The first version, the park, covered only chunked prefill. A forcing benchmark (P7) showed that it works, and also where it stops. The next spike hit a decoding request, which could not be paused, and all three requests were aborted. That led to the full cycle. It pauses and resumes requests in prefill and in decode, image prompts included, and rejects a request that can never fit with a structured error. Below is what the code does, checked against the implementation (omlx/scheduler.py, omlx/process_memory_enforcer.py, omlx/settings.py).

The first version: park a prefill

  1. Save progress while prefilling (D1, prefill_progress_commit_blocks). Every N completed blocks (4 blocks of 2048 tokens in the fork app), the prefilled blocks are stored in the paged SSD cache under the request's own block table. This needs the SSD cache. Without it the commit is skipped and a park resumes cold.
  2. Park instead of abort (T7, memory_pressure_park). At hard pressure (not emergency, and within a budget of 30 deferral polls), the memory enforcer asks the scheduler to park a victim before it considers an abort. The scheduler drops the victim's live KV cache, which frees the memory. It keeps the client stream, prompt, sampling parameters and arrival time. It pins the committed blocks against eviction, both in the in-memory block pool and in the SSD index. The request stays registered and waiting, and the client gets no error.
  3. Resume from cold cache. In the first version, a parked request was re-admitted after park_resume_ok_polls (default 3) consecutive ok polls, when the monitor went silent, or when nothing else could be admitted. The re-admission does a normal prefix lookup, which restores the committed blocks, and prefill continues from the last committed boundary. The full cycle replaced this resume rule with a memory-aware one (below).
What the evidence showed before we forced it. The park mechanism is covered by 32 test functions in tests/test_scheduler_park.py plus enforcer tests. Under normal settings it did not fire in our workload:
  • In P2 the fork finished with 0 aborts and 0 parks.
  • No live log contains a Parked request event.
  • The four live park attempts (2026-10-02) found only decoding requests and fell back to abort.
To test it deterministically we built a forcing benchmark.

The full cycle

  1. Single victim (C1). When nothing is pausable, abort one victim (largest live KV, newest on ties) instead of all. The enforcer waits for that memory to drain before it picks another. Emergency and model-unload keep abort-all. Opt-in: OMLX_MEMORY_ABORT_SINGLE_VICTIM.
  2. Decode pause and resume (C2). The pending sampled token is emitted first. The row's KV is extracted and stored as an exact SSD chain, keyed to the request and pinned, and the row leaves the batch while its stream stays open. The sampler, logits processors, stop-sequence position, parser state and remaining max_tokens are stashed. Resume restores the chain and re-inserts the row with no prefill, and the RNG is not reseeded. A singleton Lightning MTP row is first handed to standard decode. Batched MTP, DFlash, VLM-MTP and SpecPrefill rows are excluded.
  3. Memory-aware resume (C3). A paused request resumes when estimated free memory covers its need: the KV of its final length plus a transient. It never resumes at hard pressure. FIFO among paused requests, and the head-of-line hold reserves the room.
  4. Never fits vs fits later (C4). If weights + KV(prompt + max_tokens) + transient exceed capacity, the request gets HTTP 400 context_exceeds_capacity with seven numeric fields and retryable: false. A request that fits alone waits instead. GET /v1/omlx/capacity and the X-oMLX-Max-Context-Tokens header expose the numbers.
  5. Harness compaction (C5, client side). The pi extension compacts and retries on context_exceeds_capacity, and sets its compaction threshold from the capacity endpoint. It has unit tests but no live validation yet.
  6. Image prompts (C6). A text-only suffix after a cached last image is prefilled in the chunked path, so it can be paused. This route is taken only after checking that the suffix's mRoPE positions are arange + delta on every plane. Opt-in: OMLX_MEDIA_TEXT_SUFFIX_CHUNKED.

Pause and resume are behind memory_pressure_park (default off). The never-fits gate, the fits-later wait and a progress-based admission-stall clock sit behind memory_scheduling (auto | on | off, default auto). auto turns them on only when the memory guard has an explicit ceiling (the custom tier); otherwise admission stays as on main. The C7 runs all set a custom ceiling, so their evidence holds under the default.

preserve_thinking: true, measured again

The earlier result. On the 8-bit model with DFlash speculative decoding, keeping all past thinking gave near-perfect reuse, but at about 53k tokens of context the model started emitting literal </think> and raw tool-call XML as text, its draft acceptance fell from 65% to 54%, and the session did not recover. A2 was designed around that result. It keeps thinking only within the current agent loop and strips at real user messages, exactly as the template does with preserve_thinking: false. A deterministic guard strips once when retained loop thinking exceeds N tokens, then stays append-only. The guard is set to 30k.

The question. With false, every user-role message strips the reasoning of the previous segment, so the prompt shrinks and prefill restarts at the first assistant message of that segment. pi sends harness notices (todo updates, subagent results and wakes, background-job notices) as user-role messages, so they trigger the same strip. That was the last cache loss left in the parent session after the gentle-shell fix. true had never been tested for long on the current model (4-bit oQ4e with Lightning MTP), so we measured it on 2026-10-11.

Method. The installed fork.7 app was the only server running. The setting was changed at runtime through the admin API (PUT /admin/api/models/<id>/settings, which applies without a reload and persists), after a backup of the model settings. The client was the installed gentle-shell in pi RPC mode. Each pi request was joined to its server log line by its prompt and cached token counts.

  • P2, long realistic session. A fixed script of 27 real coding prompts on a scratch clone of the oMLX fork: read and explain code, find call sites, write and run unit tests, fix them, write a log parser with tests, use git. Findings.

  • No confirmed visible degeneration with true on this model up to 200k context; reasoning repetition signals remain unclassified, about 4× the point where the 8-bit DFlash setup broke. MTP acceptance stayed flat, and spot checks at 90k, 115k, 121k and 196k quoted code and file:line references from context correctly. The one slip was at 125k: the model ran a command in a documentation path quoted in the harness system prompt, then corrected itself on the next call. This is one run per setting at temperature 1.0, so it is evidence, not proof.
  • The cache gain is real but small at these segment sizes. true removed every boundary divergence, but each turn here added only 1–15k tokens, so a divergence cost a few seconds. The minutes-long re-prefill seen with false in daily use (about 560 s at 135k) needs a turn that reads tens of thousands of tokens of files before the next user message. This script did not produce one.
  • true has a cost: the context fills about 1.5× faster, because all reasoning stays in it. The model also reasoned about 2.4× more in that run, and decode slows as context grows. The same 27 prompts took 1.8× longer, and summed prefill was about equal, because true prefilled a much longer context. Part of the extra reasoning may be sampling variance.
  • Confound: the 30k retention guard stayed on in both runs. With true it never fired; the prompt never shrank.

Decision. No literal degeneration markers were observed with true in this one run on this model; reasoning repetition-detector signals remain unclassified, and these observations do not establish the absence of quality risk. On 2026-10-11 it was switched on in daily use for further observation on workloads where single turns read large files, accepting the measured context-growth and wall-time tradeoffs. The things to watch are degeneration markers, boundary TTFT, how often sessions reach compaction, and wall time per task. The A2 guard stays at 30k as a backstop.

  • Consecutive turns after the client fix: 31 of 31 strictly append-only.
  • Session-level cache efficiency on the dashboard: 95.2–95.3%.

gentle-shell: making the harness cache-friendly

This section is for the gentle-shell maintainers. The largest single cache loss in this report was in the harness, not in oMLX. While todos were open, gentle-shell's todo extension rewrote the system prompt on every user prompt. Over about 1.5 days of real use it caused about 1.05M re-prefilled tokens, roughly 80–85 minutes of GPU time, and turns that took 2–6 minutes instead of seconds. We improved the harness with the same method as the server, and the fix is ready on fix/todo-prompt-cache-1367, tracked in #1367.

The harness's existing tests did not expose the cache cost: the todo tool behaved correctly and no request failed, but some agent turns took minutes instead of seconds. We identified the cause by exercising the harness against a local inference server whose cache behaviour we could observe. Prompt-stability tests can catch the rewrite itself; server measurements establish its operational cost.

The process

The symptom

The oMLX dashboard kept showing long prefills, 40k–110k tokens, on agent turns that should have been nearly free, with concurrent requests frozen behind them. Nothing failed and every harness test passed.

Server-side evidence

oMLX's prefix-cache log states where each request diverges from the closest stored sequence. One session diverged at the same position, about token 37.7k, every few turns. A divergence at a fixed position points to something rewriting the prompt there, not to eviction.

Client-side evidence

A small pi extension recorded the exact payload of every request. Diffing consecutive requests found the first changed byte inside the system prompt, on the todo addendum's stale counter, at the same token position the server reported.

Attribution

Doing the same across all recorded sessions attributed about 945k re-prefilled tokens in main sessions and 107k in subagents to system-prompt or tool-section changes, with the todo addendum as the main driver.

Fix, test-first

Todo state moved out of the system prompt into hidden conversation messages, sent only when the list changes. The stale reminder fires once, with no counter, and the state is re-injected once after a compaction. Tests drive the extension through its public hooks and assert that the system prompt stays byte-stable.

Validation on both sides

On the client, the requests that rewrote the system prompt went from 21 of 61 to 0 of 90, and 31 of 31 consecutive turns were append-only. On the server, re-prefills above 20k tokens went from 1–2 per hour to 0.

Re-tests on upstream main

Each re-test drove the harness against the live server. One window on aa2c0389 showed no problem because its trigger never fired, and a later re-test on 43541a0d reproduced it. Our first comment was corrected publicly. The fix was rebased, its 63 todo tests pass, and it passed an independent review.

Subagents and background jobs

A full harness scenario with the fix (todo list, foreground and background subagents, a background job) kept one system prompt per session in the parent and in every child.

The last loss, shared with the server

The remaining parent cache losses came from harness notices. pi sends them as user-role messages, and the chat template strips earlier reasoning at every user-role message when preserve_thinking is off. With it on, every parent request reused its whole prefix.

The fix: keeping the system prompt stable

The gentle-shell harness appended a todo block to the system prompt on every user prompt. Once the list went stale it added a counter, (stale: N turns without an update …), that changed on every prompt. The block sat around token 30–35k of a ~41k system prompt, followed by other sections. In affected parent sessions, every tick or todo edit broke reuse of the rest of the system prompt and the conversation after it. This does not apply to every subagent: on the upstream versions examined in the re-tests, children and background jobs with GENTLE_PI_AGENTS_CHILD=1 do not load the todo hook. System-prompt or tool-section changes recorded in child traffic must therefore not all be attributed to this hook. Single turns lost 70k–110k tokens of cache this way.

We fixed it in the harness. The system prompt is now byte-stable within a session. Todo state travels as a persisted conversation message, sent only when the list actually changes. The stale reminder fires once, with no counter. After a compaction, the state is re-injected once. The fix is tested (45/45 todo tests, with the unrelated failures reproducing on a clean base), was used daily, and is proposed upstream in gentle-shell #1367. The validation below ran on the fix branch fix/todo-prompt-cache-1367 at 955523df (2026-10-05, gentle-shell 4.0.0), not on upstream main.

  • Recorded requests carrying a system-prompt mutation: 21 of 61 before, 0 of 90 after.
  • Consecutive turns that were strictly append-only after the fix: 31 of 31.
  • Server-side re-prefills above 20k tokens: they went from 1–2 per hour to 0.

Why it matters for harness projects such as gentle-shell

  • Prefix and KV caching is how both local servers (oMLX, llama.cpp, vLLM, MLX) and hosted APIs keep long agent sessions affordable. A harness that rewrites an earlier prompt prefix can increase uncached input and latency. The impact depends on each backend's caching rules, pricing and workload.
  • Ordinary todo-behaviour tests missed this interaction. A prompt-stability invariant can catch the rewrite without a server; end-to-end measurements are needed to quantify its cache and latency impact.
  • The same loop separated the causes cleanly: one was in the harness (fixed on a gentle-shell branch; still present on upstream main on 2026-10-10 and 2026-10-11), two were in the server (A1, A2), and the rest were expected (compaction, real user turns).

A proposal for gentle-shell

  • A prompt-stability invariant test. Drive N turns through the harness with fakes, and assert that each rendered request is a strict prefix-extension of the previous one, except at declared boundaries (a real user message, compaction). The #1367 fix already includes the narrow version of this for the todo tool. It could be generalized to every extension that touches the system prompt (RDD status, YOLO directive, memory).
  • An optional end-to-end check against a local server. Run a scripted session against a local OpenAI-compatible server that reports cached tokens (oMLX does, through usage.prompt_tokens_details.cached_tokens). Flag any turn whose cached-token count drops below the previous prompt length.
  • A recorder mode. An opt-in payload recorder makes this kind of diagnosis reproducible for users who report "it got slow".

Open findings

Decode fairness does not cover multimodal prompts

Any request with an image anywhere in its history carries vlm_inputs_embeds and prefills in the synchronous external loop. That happens even when every image is already inside the restored cached prefix and the uncached suffix is pure text. Both chunked branches require vlm_embeds is None, so concurrent decode freezes for the whole prefill: 25–46 s observed, and 155 s on cold 43k prefills. The fix is now built as part of the pause-resume cycle (C6, opt-in OMLX_MEDIA_TEXT_SUFFIX_CHUNKED). It routes a text-only suffix that follows a cached last image through the chunked path, after checking that the suffix positions are t + rope_delta on every mRoPE plane. Tiny-model tests show identical output with the route on and off. Its effect on the decode freezes has not been measured on hardware yet.

TurboQuant decode attention at depth

A regression over 975 single-row requests gives about 250–295 ns per context token per MTP cycle, against roughly 32 ns for a pure KV read at this model's KV size. The intercept is 70–75 ms against a weight roofline near 30 ms. These are estimates from logs. We have not yet done kernel-level profiling.

MTP depth-1 verify uses stock qmm

Depth-1 verify (M=2) runs in 97.5% of cycles, and no verify-qmm route accepts M=2: the routes cover 3–6, 4–8 and 7–24. We estimate 10–20 ms per cycle from this. MTP is still net positive in every context bucket (1.3–1.45×).

How it was validated

Evidence status. The benchmark figures, traffic counts, test-suite outcomes and pilot completion in this report are reported by the author, not an independent reproduction. A reference audit checked published link destinations, internal anchors, available code and tests, arithmetic, and the measured-to-published commit mapping. Link availability or test-source existence does not prove a run passed. This page does not currently link an immutable archive of the primary run logs, result files and exact configuration for each measurement, or an independent wiki-content audit. PR1's non-identical outputs and PR2's unexercised hardware fallback remain limitations; branch links can move, so use the commit hashes for fixed evidence.

  • Test-first. Each behaviour came with a regression test that failed before the change and passed after. The fork's full suite has 17,063 passed and 439 skipped, plus three environment-only failures (a local asset model without a chat template).
  • Independent reviews. Each slice was reviewed separately, with four review lenses on the high-risk slices. Findings fed back as small follow-up commits, for example graceful degradation when a VLM tokenizer has no encode.
  • Benchmarks against upstream. The premise harness ran upstream and fork servers in isolation, and checked that the live app was idle. It flagged contaminated runs, discarded them and reran them.
  • Recorded-traffic replay. A client-side recorder captures exact provider payloads, and a replayer re-sends them in order to an isolated server to measure reuse per build.
